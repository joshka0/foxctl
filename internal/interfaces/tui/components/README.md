# TUI Component Library — Authoring Guide for LLMs

This README is the canonical reference for LLM authors extending the foxctl
TUI operator cockpit component library. It lives at
`internal/interfaces/tui/components/` and covers package organization,
generated vs hand-written files, how to add a new widget, things you must
never do, and how to run the local test cycle.

For the full architecture decisions and rationale, see
`docs/plans/tui-redesign/architecture.md`. For the per-widget contract
(props, state, variants, keyboard behavior, focus, testing expectations), see
`docs/plans/tui-redesign/component-spec.md`.

---

## (a) Package Organization

The M2 component library lives under `internal/interfaces/tui/` in four
sub-packages:

| Package | Path | Purpose |
|---------|------|---------|
| **components** | `internal/interfaces/tui/components/` | Reusable widget primitives: EntityList, DetailPane, Tabs, Drawer, StreamViewer, EmptyState, LoadingState, StatusBadge, KeybindHint. Each widget is a struct with a `Render(buf *tui.Buffer)` method and a `HandleKey(KeyEvent)` method that returns new state. |
| **entities** | `internal/interfaces/tui/entities/` | Typed domain objects (`Agent`, `AgentNode`, `Room`, `RoomMessage`, `EventRow`) and the `EntryKind` typed enum (18 named constants replacing string-keyed kinds). Use `ParseEntryKind(s)` to convert legacy wire-format strings. |
| **runtime** | `internal/interfaces/tui/runtime/` | Generic `Bounded[Req, Upd]` — the shared bounded-runtime primitive that replaces duplicated goroutine scaffolding. Exposes `Enqueue`, `Updates`, `Stop`, `Close`. |
| **theme** | `internal/interfaces/tui/theme/` | Color palette (`theme.Colors`) and spacing tokens (`theme.Spacing`). All widgets must reference tokens by name (e.g., `theme.Colors.Accent`). Raw color literals are forbidden. |

Additionally, the legacy shell surface lives alongside these packages:

| File | Purpose |
|------|---------|
| `internal/interfaces/tui/shell.gsx` | Legacy companion shell `.gsx` source template (editable) |
| `internal/interfaces/tui/shell_gsx.go` | Generated from `shell.gsx` (DO NOT EDIT) |
| `internal/interfaces/tui/shell_state.go` | Legacy companion state management |
| `internal/interfaces/tui/keys.go` | Global keybinding constants |
| `internal/interfaces/tui/live_state.go` | Live daemon state polling |
| `internal/interfaces/tui/api_client.go` | HTTP client for daemon API |
| `internal/interfaces/tui/agent_adapter.go` | Agent API adapter |
| `internal/interfaces/tui/console_*.go` | Console runtimes (delegating to `runtime.Bounded`) |
| `internal/interfaces/tui/smoke_*.go` | Smoke-mode entry points (`-smoke-agent`, `-smoke-console`) |

## (b) Generated vs Hand-Written Files

Understanding which files are generated is critical — editing a generated file
means your changes will be silently overwritten on the next `tui generate` run.

### Generated files (NEVER hand-edit)

| File | Source |
|------|--------|
| `internal/interfaces/tui/shell_gsx.go` | `shell.gsx` |
| Any file with header `// Code generated by tui generate. DO NOT EDIT.` | Its corresponding `.gsx` source |

When new `.gsx` files are added in M3+, their `*_gsx.go` counterparts join
this table.

### Hand-written files (safe to edit)

- `*.go` in `components/`, `entities/`, `runtime/`, `theme/` — all hand-written
- `*_test.go` files — always hand-written
- `*.gsx` files — the source-of-truth templates; edit these directly
- `cmd/` subdirectories — standalone TUI demo binaries for tuistory

### .gsx regeneration command

```bash
# Option 1: via go generate
go generate github.com/grindlemire/go-tui/cmd/tui@v0.11.0 ./internal/interfaces/tui/...

# Option 2: if the tui CLI is installed
tui generate ./internal/interfaces/tui/...
```

Both `.gsx` source and `*_gsx.go` generated files must be committed in the
same commit (VAL-CROSS-004).

## (c) How to Add a New Widget

Follow these steps precisely. Every step is required; skipping tests is not
acceptable.

### Step 1: Write the failing tests first (Red)

Create `<widget_name>_test.go` in `components/`. Use the `tui.MockTerminal`
pattern established by existing widgets:

```go
package components

import (
    "testing"
    "github.com/grindlemire/go-tui"
    "github.com/joshka0/foxctl/internal/interfaces/tui/theme"
)

// renderMyWidget is a test helper that renders the widget into a MockTerminal.
func renderMyWidget(w MyWidget, width, height int) *tui.MockTerminal {
    mt := tui.NewMockTerminal(width, height)
    buf := tui.NewBuffer(width, height)
    w.Render(buf)
    tui.RenderFull(mt, buf)
    return mt
}

func TestMyWidget_RendersContent(t *testing.T) {
    t.Parallel()
    w := NewMyWidget("hello", 40, 5)
    mt := renderMyWidget(w, 40, 5)
    // Assert visible content in the terminal buffer
    if !strings.Contains(mt.StringTrimmed(), "hello") {
        t.Error("expected content 'hello' in output")
    }
}
```

Required test coverage per widget:

1. **Focus indicator** — verify the widget shows a visible focus indicator
   (colored border, inverse background, etc.) that is NOT font-weight only.
2. **Keyboard navigation** — test every documented key binding.
3. **Empty state** — what renders when the widget has no data.
4. **Loading state** — what renders while data is being fetched.
5. **Error state** — what renders on failure.
6. **Wrap-around** — if the widget has cyclic navigation (e.g., tabs, lists),
   test that wrap-around behaves as documented.
7. **Overflow / scrolling** — if the widget scrolls, test that content outside
   the viewport is accessible and scroll indicators appear.
8. **Width boundary** — verify truncation with ellipsis at narrow widths.

### Step 2: Create the snapshot test file

Create `<widget_name>_snapshot_test.go` that writes golden snapshots to
`testdata/snapshots/`:

```go
func TestSnapshotMyWidgetDefault(t *testing.T) {
    w := NewMyWidget("content", 40, 5, WithFocused(true))
    mt := renderMyWidget(w, 40, 5)
    writeSnapshot(t, "mywidget-default.txt", mt.StringTrimmed())
}
```

The `writeSnapshot` helper is defined in the existing snapshot test files and
writes to `testdata/snapshots/<name>.txt`.

### Step 3: Implement the widget (Green)

Create `<widget_name>.go`. Follow these conventions:

- **Constructor**: `NewMyWidget(props..., width, height int, opts ...MyWidgetOption) *MyWidget`
  using functional options for optional configuration.
- **Render method**: `func (w *MyWidget) Render(buf *tui.Buffer)` — renders into
  the buffer using `tui.NewStyle()` with theme tokens.
- **Key handler**: `func (w *MyWidget) HandleKey(e tui.KeyEvent)` — returns
  updated state; never performs I/O.
- **Theme tokens only**: import `theme` and use `theme.Colors.*` and
  `theme.Spacing.*`. Never use raw `tui.Cyan`, `tui.Red`, hex strings, etc.
- **Stateless render**: the `Render` method reads from struct fields and writes
  to the buffer. No side effects, no I/O, no `time.Now()`, no `rand.*`.

```go
package components

import (
    "github.com/grindlemire/go-tui"
    "github.com/joshka0/foxctl/internal/interfaces/tui/theme"
)

type MyWidget struct {
    label  string
    width  int
    height int
    focused bool
}

type MyWidgetOption func(*MyWidget)

func WithMyWidgetFocused(f bool) MyWidgetOption {
    return func(w *MyWidget) { w.focused = f }
}

func NewMyWidget(label string, width, height int, opts ...MyWidgetOption) *MyWidget {
    w := &MyWidget{label: label, width: width, height: height}
    for _, opt := range opts {
        opt(w)
    }
    return w
}

func (w *MyWidget) Render(buf *tui.Buffer) {
    style := tui.NewStyle().Foreground(theme.Colors.TextPrimary)
    if w.focused {
        style = style.Background(theme.Colors.SelectionBg)
    }
    buf.SetLine(0, tui.Line{tui.Cell{Text: w.label, Style: style}})
}

func (w *MyWidget) HandleKey(e tui.KeyEvent) {
    // Pure state mutation only — no I/O
}
```

### Step 4: Create a tuistory demo binary (optional, for snapshot capture)

If the widget needs tuistory snapshot captures, create
`cmd/<widgetname>/main.go` following the pattern in `cmd/entitylist_tui.go`.
This is a standalone go-tui app that renders the widget for the tuistory
harness to capture.

### Step 5: Run the tests

```bash
# Unit tests + snapshots
go test -race -count=1 ./internal/interfaces/tui/components/...

# Full TUI package (catches regressions)
go test -race -count=1 ./internal/interfaces/tui/...
```

Both must pass before committing.

### Step 6: Commit

Commit all new files together:
```
git add internal/interfaces/tui/components/my_widget.go
git add internal/interfaces/tui/components/my_widget_test.go
git add internal/interfaces/tui/components/my_widget_snapshot_test.go
git add internal/interfaces/tui/components/testdata/snapshots/mywidget-*.txt
git commit
```

## (d) Explicit "Do Not" List

These rules are enforced by validation (VAL-CROSS-006, VAL-CMP-010) and
scrutiny review. Violations will cause the mission to fail validation.

| # | Rule | Why |
|---|------|-----|
| 1 | **Do not edit `*_gsx.go` files** | They are generated from `.gsx` sources. Your changes will be silently overwritten by `tui generate`. Edit the `.gsx` source instead. |
| 2 | **Do not use `time.Now()` in render or reducer code** | Breaks determinism. Inject a clock via the constructor instead. `time.Now()` in test files is acceptable. |
| 3 | **Do not use `rand.*` in render or reducer code** | Breaks determinism. Pre-generate random values in tests or inject a random source via constructor. |
| 4 | **Do not use `os.Getenv` in render or reducer code** | Environment access is I/O. Read env vars in the shell/adapter layer and pass values as constructor parameters. |
| 5 | **Do not use raw color literals** | No `tui.Cyan`, `tui.Red`, `"#rrggbb"`, or ANSI indices in `components/` widget implementations. Import and use `theme.Colors.*` tokens exclusively. The `theme/` package itself is the only exempt location. |
| 6 | **Do not perform I/O in `Render()` or `HandleKey()`** | No HTTP calls, file reads, env access, or channel sends in render/key-handling methods. These must be pure functions of their inputs. |
| 7 | **Do not create unbounded channels** | All channels must be bounded with an explicit backpressure policy. Use `make(chan T, N)` where N is documented and finite. |
| 8 | **Do not use shared mutable maps without a single-owner goroutine** | Cross-goroutine state must go through channels, not shared maps. Single-writer state ownership is mandatory. |
| 9 | **Do not add new dependencies** | The framework is pinned to `github.com/grindlemire/go-tui v0.11.0`. No new Go module dependencies. |
| 10 | **Do not modify files under `archive/`, `packages/gui-agent/`, or `internal/interfaces/web/`** | These are mission boundaries. See mission AGENTS.md. |

## (e) Running the Local Test Cycle

Use these exact commands. They are the validation gates that must pass before
any commit.

### Unit tests (fast, run often)

```bash
# Components only (fastest, ~2s)
go test -race -count=1 ./internal/interfaces/tui/components/...

# Full TUI package including runtime, entities, theme (~5s)
go test -race -count=1 ./internal/interfaces/tui/...
```

### Lint and format

```bash
# Format code
gofumpt -w ./internal/interfaces/tui/

# Lint (if golangci-lint is compatible with the Go toolchain)
golangci-lint run --timeout 10m ./internal/interfaces/tui/...
```

### Doc link check (required if you change any `.md` files)

```bash
make check-doc-links
```

### Full validation (run before handoff)

```bash
# The comprehensive check target
make check
```

### Build the TUI binary

```bash
go build -o bin/foxctl_tui ./cmd/foxctl_tui
```

### Smoke modes (verify existing surfaces still work)

```bash
# Build first
make go-tui-build

# Run smoke modes (exit cleanly without a reachable API)
./bin/foxctl-tui --smoke-agent
./bin/foxctl-tui --smoke-console
```

## Authoring Walkthrough: Adding a FooBadge Widget

This walkthrough answers the question "how would I add a `FooBadge` widget?"
using only this README and the M1 docs under `docs/plans/tui-redesign/`.

### 1. Check the component spec

Read `docs/plans/tui-redesign/component-spec.md` and find the section for
the most similar existing widget. FooBadge is closest to `StatusBadge` — a
small, stateless inline indicator. The component spec defines the required
props, state, variants, keyboard behavior, focus behavior, and testing
expectations.

### 2. Write the failing tests

Create `internal/interfaces/tui/components/foo_badge_test.go`:

```go
package components

import (
    "testing"
    "github.com/grindlemire/go-tui"
    "github.com/joshka0/foxctl/internal/interfaces/tui/theme"
)

func TestFooBadge_RendersLabel(t *testing.T) {
    t.Parallel()
    fb := NewFooBadge(FooBadgeVariantActive, "active-foo", 0)
    mt := renderSmallWidget(fb, 20, 1)
    if !strings.Contains(mt.StringTrimmed(), "active-foo") {
        t.Error("expected label 'active-foo' in output")
    }
}

func TestFooBadge_EachVariantDistinctColor(t *testing.T) {
    t.Parallel()
    variants := []FooBadgeVariant{FooBadgeActive, FooBadgeInactive, FooBadgeWarning}
    colors := map[FooBadgeVariant]tui.Color{}
    for _, v := range variants {
        fb := NewFooBadge(v, "x", 0)
        mt := renderSmallWidget(fb, 20, 1)
        // Inspect raw buffer to extract foreground color
        // (follow the pattern in small_primitives_test.go)
        _ = mt
        colors[v] = fooBadgeColor(v) // use the same function the impl uses
    }
    // Assert all three variants have distinct colors
    seen := map[tui.Color]bool{}
    for v, c := range colors {
        if seen[c] {
            t.Errorf("variant %v has duplicate color with another variant", v)
        }
        seen[c] = true
    }
}
```

### 3. Create the snapshot test file

Create `internal/interfaces/tui/components/foo_badge_snapshot_test.go`:

```go
func TestSnapshotFooBadgeActive(t *testing.T) {
    fb := NewFooBadge(FooBadgeActive, "active", 0)
    mt := renderSmallWidget(fb, 20, 1)
    writeSnapshot(t, "foobadge-active.txt", mt.StringTrimmed())
}

func TestSnapshotFooBadgeInactive(t *testing.T) {
    fb := NewFooBadge(FooBadgeInactive, "inactive", 0)
    mt := renderSmallWidget(fb, 20, 1)
    writeSnapshot(t, "foobadge-inactive.txt", mt.StringTrimmed())
}
```

### 4. Implement the widget

Create `internal/interfaces/tui/components/foo_badge.go`:

```go
package components

import (
    "github.com/grindlemire/go-tui"
    "github.com/joshka0/foxctl/internal/interfaces/tui/theme"
)

type FooBadgeVariant int

const (
    FooBadgeActive   FooBadgeVariant = iota
    FooBadgeInactive
    FooBadgeWarning
)

type FooBadge struct {
    variant FooBadgeVariant
    label   string
    width   int
}

func NewFooBadge(variant FooBadgeVariant, label string, width int) *FooBadge {
    return &FooBadge{variant: variant, label: label, width: width}
}

func (fb *FooBadge) Render(buf *tui.Buffer) {
    color := theme.Colors.Accent
    switch fb.variant {
    case FooBadgeInactive:
        color = theme.Colors.TextMuted
    case FooBadgeWarning:
        color = theme.Colors.StatusWarn
    }
    style := tui.NewStyle().Foreground(color)
    buf.SetLine(0, tui.Line{tui.Cell{Text: fb.label, Style: style}})
}
```

Key points:
- Import `theme` and use `theme.Colors.*` — no raw color literals.
- `Render()` is pure: no I/O, no `time.Now()`, no `rand.*`, no `os.Getenv`.
- Constructor accepts all configuration as parameters — no ambient state.

### 5. Run the tests

```bash
go test -race -count=1 ./internal/interfaces/tui/components/...
```

Confirm all tests pass including the new FooBadge tests.

### 6. Commit

```bash
git add internal/interfaces/tui/components/foo_badge.go
git add internal/interfaces/tui/components/foo_badge_test.go
git add internal/interfaces/tui/components/foo_badge_snapshot_test.go
git add internal/interfaces/tui/components/testdata/snapshots/foobadge-*.txt
git commit
```

No `.gsx` regeneration is needed because FooBadge is a pure Go widget, not a
`.gsx` view. The regeneration command (`tui generate ./internal/interfaces/tui/...`)
only applies when you create or modify `.gsx` files.

## Authoring Walkthrough: Adding a Rooms Screen

This walkthrough answers "how would I add a Rooms screen?" using only this
README and the M1 docs under `docs/plans/tui-redesign/`.

A Rooms screen is a full view (not a small widget), so it involves the `.gsx`
toolchain in addition to the component library.

### 1. Design the screen

Read these M1 docs to understand the full context:
- `docs/plans/tui-redesign/information-architecture.md` — the Rooms secondary
  flow outline (section (c)) and the screen inventory (section (g)).
- `docs/plans/tui-redesign/component-spec.md` — the widget contracts you'll
  compose.
- `docs/plans/tui-redesign/integration-map.md` — the API endpoints for rooms
  (`GET /api/rooms`, `GET /api/rooms/{id}/events`).

### 2. Create the state and adapter

These are hand-written Go files:

**`internal/interfaces/tui/rooms_state.go`** — immutable state struct with a
single `Reduce(action) RoomsState` method. No I/O, no `time.Now()`.

**`internal/interfaces/tui/rooms_adapter.go`** — uses `api_client.go` to fetch
rooms from the daemon. Injects results into the state reducer. Runs inside a
`runtime.Bounded[Req, Upd]` instance.

### 3. Create the `.gsx` source

**`internal/interfaces/tui/rooms_screen.gsx`** — defines the `RoomsScreen`
component struct and its `Render()` template. Composes M2 widgets:
- `EntityList` for the room directory.
- `DetailPane` for the selected room's details and membership.
- `StreamViewer` for the per-room event stream.

### 4. Run the `.gsx` regeneration

```bash
tui generate ./internal/interfaces/tui/...
```

This produces `internal/interfaces/tui/rooms_screen_gsx.go`. Verify it has the
generated-file header:

```go
// Code generated by tui generate. DO NOT EDIT.
// Source: rooms_screen.gsx
```

### 5. Write tests

**`internal/interfaces/tui/rooms_screen_test.go`** — MockTerminal-based unit
tests covering:
- Empty room list (uses `EmptyState`).
- Loading state while fetching.
- Room selection populates detail pane.
- Event stream rendering.
- Keyboard navigation and keybindings.

**`internal/interfaces/tui/rooms_adapter_test.go`** — adapter tests using
`httptest.NewServer` to mock the daemon's `/api/rooms` endpoint.

### 6. Register the screen

Wire the `RoomsScreen` into the cockpit's runtime registry (see architecture.md
Decision (b)) and add navigation keybindings per the information-architecture
keybinding table.

### 7. Run tests and commit

```bash
go test -race -count=1 ./internal/interfaces/tui/...
```

Commit both `.gsx` and `*_gsx.go` in the same commit:

```bash
git add internal/interfaces/tui/rooms_screen.gsx
git add internal/interfaces/tui/rooms_screen_gsx.go
git add internal/interfaces/tui/rooms_state.go
git add internal/interfaces/tui/rooms_adapter.go
git add internal/interfaces/tui/rooms_screen_test.go
git add internal/interfaces/tui/rooms_adapter_test.go
git commit
```

### 8. Verify doc links

If you added or modified any markdown documentation:

```bash
make check-doc-links
```
