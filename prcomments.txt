**Stop can race with dispatchNext and panic by sending on a closed channel**
`Stop` closes `workCh`:
```go
func (s *WFQScheduler) Stop() {
    ...
    close(s.stopCh)
    close(s.workCh)
}
```
But `schedulerLoop` can still wake on the ticker *after* `Stop` has closed `workCh` and call `dispatchNext`, which does:
```go
select {
case s.workCh <- job:
default:
    heap.Push(s.globalQueue, job)
}
```
A send on a closed channel panics (`send on closed channel`), so there’s a real race between `Stop` and `dispatchNext`.
A simple, safe fix is to only close `stopCh` and let workers exit via the stop signal (and `ctx.Done()`), leaving `workCh` open:
```diff
 func (s *WFQScheduler) Stop() {
 	s.mu.Lock()
 	if !s.running {
 		s.mu.Unlock()
 		return
 	}
 	s.running = false
 	s.mu.Unlock()
-	close(s.stopCh)
-	close(s.workCh)
+	close(s.stopCh)
 }
```
Because workers’ `select` includes `<-s.stopCh`, closing `stopCh` is sufficient to cause them to exit without needing to close `workCh`, and it removes the possibility of writing to a closed channel.
