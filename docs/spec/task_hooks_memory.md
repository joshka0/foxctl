# SPEC-XXX: Task-Aware Hooks & Memory Integration

**Status:** Draft\
**Owner:** TBD\
**Applies to:** agentctl (Core + Agent Profile), Claude harness integration

---

## 1. Goals

### 1.1 Primary Goals

- **G1: Task-Centric Traceability**\
  Every state-changing operation (edits, writes, tests, jobs) performed via
  Claude + agentctl is associated with a concrete `task_id`.

- **G2: Hook-First Integration**\
  Claude Code hooks are thin bash wrappers that call agentctl skills. All real
  logic (task gating, quality checks, context, memory, async work) lives in Go.

- **G3: Unified Storage Model**\
  Tasks, jobs, CAS metadata, and agent coordination (mailbox/blackboard) can all
  be queried and joined via SQLite/Turso, using shared identifiers (`task_id`,
  `workspace_id`).

- **G4: Optional Cloud Memory**\
  Local correctness must not depend on networked storage. Turso-backed memory
  (with vectors) is an _optional_ upgrade for smarter recall and cross-machine
  collaboration.

### 1.2 Non-Goals

- Replacing existing mailbox/blackboard semantics.
- Implementing a full-featured project management system.
- Hard dependency on Turso for basic workflows.

## 2. Invariants & Terminology

### 2.1 Invariants

- **I1: Workspace Detection**\
  agentctl maintains a normalized `workspace_id` per process based on the
  detected workspace root (e.g. git worktree root). Different git worktrees =
  different `workspace_id`s.

- **I2: Single Active Task per Workspace**\
  At any given time, there is at most one `active_task` for a given
  `workspace_id`. Multiple tasks may be open; only one is the current focus.

- **I3: Writes Require an Active Task**\
  Any state-changing action initiated via hooks (e.g. file edits, multi-edits,
  Bash commands that modify the tree) must have an associated `task_id` for that
  `workspace_id` by the time it executes.

- **I4: Read Operations Are Always Allowed**\
  Non-mutating operations (fs/ls, fs/read, grep, etc.) must never be blocked by
  task gating.

- **I5: Backend Agnostic**\
  All task, hook, and memory features must function with `sqlite` backends. When
  `turso` is configured, memory-related features may be enhanced (e.g. vector
  search), but behavior remains compatible.

### 2.2 Identifiers

- **`workspace_id`**: Canonical identifier for a workspace/worktree
  (implementation detail; likely derived from absolute root path + hashing).
- **`task_id`**: ULID generated by `todo/manage` when tasks are created. Unique
  per agentctl installation; practical collisions across machines are ignored
  for now.
- **`scope_path`**: Optional relative path within the workspace indicating where
  the task is primarily focused (e.g. `services/api/`).

## 3. Task Model in `todo/manage`

### 3.1 Current Behavior (Summary)

- Skill: `todo/manage` (exec skill)
- Operations: `add|complete|list`
- Storage: JSON-backed store under `~/.agentctl/todo/tasks.json` (subject to
  change under this spec).

### 3.2 Proposed Extensions

#### 3.2.1 Persisted Task Store

- Migrate `todo/manage` to a proper SQLite-backed store, managed via agentctl's
  storage layer.
- Tables (high-level):
  - `tasks`:
    - `id` (TEXT, ULID, PK)
    - `workspace_id` (TEXT, indexed)
    - `title` (TEXT)
    - `description` (TEXT)
    - `scope_path` (TEXT, nullable)
    - `status` (TEXT: `open|completed|archived`)
    - `created_at`, `completed_at` (TIMESTAMP)
    - `parent_id` (TEXT, nullable)
  - `task_notes` (optional, later):
    - `id`, `task_id`, `note`, `created_at`.

#### 3.2.2 New Operations

Extend the `todo/manage` skill signature to support:

- `operation: get_active`
  - Input:
    - `workspace_id` (string; derived internally when called from CLI/hooks)
  - Output:
    - `task` object or `null`.

- `operation: set_active`
  - Input:
    - `workspace_id`
    - `task_id`
  - Behavior:
    - Sets the specified task as active for the workspace.
    - Enforces invariant: at most one active task per workspace.

- `operation: ensure_active`
  - Input:
    - `workspace_id`
    - `default_title` (string)
    - `scope_path` (optional)
  - Behavior:
    - If an active task exists: return it.
    - Else: create a new `open` task with the given title/scope, set active,
      return it.

> Implementation detail: Active-task pointers may be modeled either via a
> `workspace_active_tasks` table or via a field on `tasks` (e.g. `is_active`
> with a uniqueness constraint per `workspace_id`). Choice is left to
> implementation as long as I2 is enforced.

## 4. Hook Skills & Bash Wrappers

### 4.1 Claude Hook Wrappers

Claude Code hooks are configured to call small bash scripts under
`.claude/hooks/`:

- Each script:
  - Reads hook payload JSON from `stdin`.
  - Optionally takes the hook event as `$1`.
  - Calls `agentctl run <hook-skill> --input-file -`.
  - Extracts `data.hook_output` from the resulting envelope and emits it as the
    hook's stdout JSON.

Example (conceptual):

```bash
#!/usr/bin/env bash
set -euo pipefail

HOOK_EVENT="${1:-PostToolUse}"
AGENTCTL_BIN="${AGENTCTL_BIN:-agentctl}"

payload="$(cat)"

result="$(printf '%s' "$payload" | "$AGENTCTL_BIN" run hooks/task_guard --input-file -)"

hook_json="$(printf '%s' "$result" | jq -c '.data.hook_output // {}')"

printf '%s\n' "$hook_json"
```

### 4.2 Hook Input/Output Contracts

Define shared types in `internal/domain/hook` (names illustrative):

```go
type Input struct {
    Event          string          `json:"event"`           // e.g. "UserPromptSubmit", "PreToolUse"
    WorkspaceRoot  string          `json:"workspace_root"`
    SessionID      string          `json:"session_id"`
    TranscriptPath string          `json:"transcript_path"`
    ToolName       string          `json:"tool_name,omitempty"`
    ToolInput      json.RawMessage `json:"tool_input,omitempty"`
    ToolResponse   json.RawMessage `json:"tool_response,omitempty"`
}

type Output struct {
    Decision string                 `json:"decision"`           // "approve"|"block"|"none"
    Reason   string                 `json:"reason,omitempty"`
    Context  string                 `json:"context,omitempty"`  // supplemental text for Claude
    Meta     map[string]any         `json:"meta,omitempty"`
}
```

Hook skills always emit standard envelopes where `data.hook_output` is a
`hook.Output`.

## 5. Task-Aware Hook Skills

### 5.1 `hooks/task_guard`

**Event:** `PreToolUse` (matcher: `Edit|Write|MultiEdit|Bash` etc.)\
**Purpose:** Enforce invariant I3 (writes require an active task) and provide a
UX path for auto-creating tasks.

**Inputs:**

- `hook.Input` (from wrapper), including `WorkspaceRoot` and `ToolName`.
- Config (env or config file) for behavior:
  - `AGENTCTL_TASK_GUARD_MODE`:
    - `auto` (default): auto-create tasks when none exist.
    - `strict`: block and require explicit task creation.

**Behavior (auto mode):**

1. Resolve `workspace_id` from `WorkspaceRoot` via workspace detection.
2. Call `todo/manage` with `operation: ensure_active`.
   - `default_title` heuristic: derive from tool + file path or last prompt
     summary.
3. Return `hook.Output` with:
   - `decision: "approve"`
   - `reason: "task ensured"`
   - `meta.task_id`, `meta.workspace_id`.

**Behavior (strict mode):**

1. Resolve `workspace_id`.
2. Call `todo/manage` with `operation: get_active`.
3. If active exists → `approve` with task metadata in `meta`.
4. Else → `block` with guidance in `reason` (e.g. "No active task. Use agentctl
   todo add ... or /start-task").

Hook semantics are limited to `hook.Output` (`DecisionApprove`/`DecisionBlock`).
Callers that translate a `DecisionBlock` into a top-level tool error SHOULD use
`E_GUARD_VIOLATION` as the error code (see `dspy_go_agents.md` §11.3),
indicating a guard/scope violation rather than a transient runtime failure.

### 5.2 `hooks/task_update` (optional initial scope)

**Event:** `PostToolUse` (for edits/writes)\
**Purpose:** Append context to the active task (notes, changed files, test
results).

**Behavior (MVP):**

- Resolve `workspace_id` and active `task_id`.
- Extract high-level info from `ToolInput` / `ToolResponse`:
  - Files touched, command run, success/failure.
- Call `todo/manage` (e.g. new `operation: add_note`) to persist a short note
  tied to `task_id`.
- Return `approve` with minimal `reason`.

Details for note schema are deferred; initial implementation can be a no-op hook
that simply logs to CAS while we refine the UX.

## 6. Memory & Embeddings

### 6.1 Local vs Global Memory

- **Local (required):**
  - Memory entries for recent work, task notes, and CAS metadata must be stored
    in a way that works with SQLite.
  - This allows offline + single-machine workflows to remain fully functional.

- **Global (optional):**
  - When `AGENTCTL_MEMORY_DB_DRIVER=turso`, the memory store may use
    Turso/libSQL, including vector search when
    `AGENTCTL_MEMORY_VECTOR_SEARCH=true`.
  - Cross-machine collaboration is enabled by pointing multiple agentctl
    instances at the same MEMORY DB.

### 6.2 Task-Aware Memory Entries

When hook skills persist context to memory (e.g. summaries, diffs, test logs),
entries should include:

- `workspace_id`
- `task_id`
- `kind` (e.g. `"diff"`, `"test_output"`, `"note"`)
- `summary` (short text)
- Optional `embedding` (when vector search is enabled)

API-level, this can be modeled using the existing memory store interfaces (e.g.
named entries, vector entries) by:

- Encoding `workspace_id` + `task_id` into names and/or tags.
- Using `memory.VectorEntry` when embeddings are available.

### 6.3 Retrieval in Hooks

A future `hooks/context_inject` skill can:

1. Receive `hook.Input` (including current file, tool, prompt context).
2. Form a query embedding (implementation-specific; may call an LLM or embedding
   service).
3. Query the memory/vector store for similar entries scoped to
   `(workspace_id, task_id)`.
4. Stitch top-K entries into a compact `context` string for
   `hook.Output.Context`.

This mechanism should be implemented via the memory abstraction layer so that:

- On SQLite: search may be approximate or fallback to keyword-based.
- On Turso: native vector indices are used when configured.

## 7. Interaction with Mailbox & Blackboard

### 7.1 Mailbox (Inter-Agent Messaging)

- No schema changes required.
- Recommendation: when agents send mailbox messages related to a task, include:
  - `headers["task_id"] = <task_id>`
  - `headers["workspace_id"] = <workspace_id>`

This enables downstream processing and auditing to tie conversations back to
tasks.

### 7.2 Blackboard (Shared Topic Bus)

- No schema changes required.
- Recommendation: when hook or agent workflows post blackboard items
  representing work units:
  - Include `task_id` and `workspace_id` fields in the JSON payload.
  - Optionally use topics that encode coarse-grained categories (e.g.
    `"code.quality"`, `"docs.update"`).

Hooks that offload heavy work (e.g. deep analysis) can create blackboard records
instead of blocking Claude, while still preserving task-level traceability.

## 8. Rollout Plan (High-Level)

1. **Spec Finalization**
   - Validate invariants and scope with stakeholders.

2. **Task Store & `todo/manage` Extensions**
   - Implement SQLite-backed task store.
   - Add `get_active`, `set_active`, `ensure_active` operations.

3. **Hook Domain Types & Base Skill Wiring**
   - Add `internal/domain/hook` types.
   - Implement initial `hooks/task_guard` skill.

4. **Claude Hook Wrappers (Bash)**
   - Add `.claude/hooks/task-guard.sh` using the standard wrapper pattern.
   - Update `.claude/settings.json` in harness example to wire `PreToolUse` →
     `task_guard`.

5. **Task Update Hook (Optional MVP)**
   - Implement `hooks/task_update` skill and wire `PostToolUse` for edits.

6. **Memory & Embedding Integration (Phase 2)**
   - Standardize task-aware memory/embedding entries.
   - Implement `hooks/context_inject` prototype.

7. **Mailbox/Blackboard Tagging (Phase 3)**
   - Update agent workflows to include `task_id`/`workspace_id` in
     headers/payloads when applicable.

  nearest open task by path), or remain informational only in v1?
- **Q2:** How opinionated should the auto-generated task titles be (tool+path vs
  LLM-summarized prompt)?
- **Q3:** Do we need a user-facing way to inspect `active_task` state from the
  CLI (e.g. `agentctl todo active`)?
- **Q4:** What is the minimal useful `hooks/task_update` behavior for v1 (just
  CAS logging vs richer note-taking)?
