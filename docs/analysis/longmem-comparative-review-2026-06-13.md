> Comparison of agent-oss ("Quarq Agent") and HydraDB v2 against foxctl's
> current long-term-agent memory work, to determine how to get foxctl longmem
> working properly. Companion to
> [long-term-agent-worktree-status-2026-06-11.md](long-term-agent-worktree-status-2026-06-11.md).
> Code citations verified against branch `feat/ci-core-skills-split`.

## 1. TL;DR

foxctl's biggest missing piece is a **self-correcting retrieval loop with semantic evidence matching**. The architecture is actually *more* sophisticated than Quarq in lifecycle/provenance terms (typed claims, impact graph, certification), but it is brittle at the two points that decide LongMem accuracy: (a) the evidence ledger uses regex/substring slot-matching (`classifyEvidenceLedgerRow` in `internal/rlm/env/tool_exec.go:7922`), which violates foxctl's own "no keyword heuristics" rule and false-rejects conversational evidence; and (b) there is no fallback re-query when retrieval is insufficient — foxctl either finds it or guesses, whereas Quarq's `REQUIRED_DATA` protocol re-searches on the LLM's own self-identified target nouns. The highest-leverage moves, in order: replace ledger substring slot-matching with embedding-based semantic term matching; add a `REQUIRED_DATA`-style targeted fallback re-query in the RLM runner; lower/adapt the named-memory candidate lifecycle gate (hardcoded `0.9` in `memoryrecall/search.go:22`) and wire named-memory recall as a first-class mixed lane; and close the bidirectional feedback loop so answer-mode `accepted_ledger_evidence` auto-emits `RetrievalFeedback.UsedRefs` to promote candidate claims. Borrow Quarq's *mechanisms* (HyDE decomposition, REQUIRED_DATA, dynamic thresholds, temporal anchoring) and HydraDB's *design ideas* (valid-time graph edges, decay-with-reinforcement, context-enriched chunking) — but adopt neither product, since FAISS/LangGraph and HydraDB's hosted REST both violate foxctl's CGO-off + no-egress posture.

## 2. How the three systems compare

| Dimension | foxctl (current) | Quarq (agent-oss) | HydraDB v2 |
|---|---|---|---|
| Memory typing | Typed `MemoryClaim` + Kind taxonomy, full lifecycle FSM | 3 hard tiers: semantic / episodic / procedural | Dual store: shared Knowledge vs per-user Memories + `infer` flag |
| Retrieval | 5 lanes + mixed; BM25+vector hybrid fusion (0.45/0.55) | HyDE 4–5 query decomposition, vector+keyword, dedup by ID | Triple-stream fusion (vector + entity-path graph + entity-expansion) + cross-encoder rerank |
| Self-correcting retrieval | **None** — no re-query on miss | `REQUIRED_DATA` protocol: LLM flags insufficiency, re-searches on extracted target nouns | `mode=thinking` graph expansion (no explicit insufficiency flag) |
| Temporal/numeric | Validity windows, supersession, staleness markers; numeric handled by regex in ledger | Strict narrative-date vs storage-date split; numeric exactness scopes (exact/qualified/range/vague) | Bitemporal valid-time edges; `recency_bias` knob; decay engine |
| Evidence attribution | Surfaced/accepted/cited separation; ledger ACCEPT/REJECT via **regex slot-matching** | Thinking-block evidence table (25-row hard cap), entity-isolation, ACCEPT-only calculation | Structural tenant/sub-tenant isolation (not filter-based) |
| Storage substrate | SQLite/CAS/Turso, async embedding queue, local-first | Local JSON + FAISS (`IndexFlatIP`), OpenAI embeddings | Hosted REST only; no Go SDK; no on-prem |

The key insight: **foxctl already wins on the structural/lifecycle layer** that Quarq lacks entirely (Quarq has no refutation/conflict graph, no certification, simple tag-based procedural rules). foxctl *loses* on the retrieval-and-verification dynamics that actually move benchmark numbers. Quarq scores 98% on LongMemEval-S not because of richer storage but because of its closed-loop grounding: HyDE decomposition widens recall, dynamic thresholds adapt depth, and REQUIRED_DATA refuses to guess. HydraDB's 90.79% comes from graph-fused retrieval — but it is a hosted network service with no Go SDK and no self-host path, making it an architectural non-starter for foxctl; only its *design ideas* transfer.

## 3. Why foxctl's four cases fail

**1. Coupon case — ledger false negative.** Evidence "I redeemed a $5 coupon on coffee creamer through Target checkout" is rejected because `classifyEvidenceLedgerRow` (`internal/rlm/env/tool_exec.go:7922`, called from `buildEvidenceLedger` at `:7839`) does token/substring slot-matching that assumes co-location of "coupon" and "Target" in the same clause. This is exactly the keyword-heuristic pattern foxctl's own AGENTS.md bans. **Fix it with Quarq's evidence-table grounding philosophy** (bind requested target, ACCEPT on semantic entity match not substring) implemented as **embedding-based term matching** rather than Quarq's prompt-only approach — and HydraDB's entity-anchored matching as the conceptual model.

**2. Degree case — retrieval query-planning miss.** Named-memory recall is optional and delegated to a `ContextPackFunc` fallback rather than wired as a first-class lane (`retrieve_lanes.go`); query tokens don't align with conversational session text. **Quarq's HyDE relational decomposition** (Query 2/3 entity-vs-action split) plus **dynamic deep-mode threshold (0.28)** for exploratory/categorical questions addresses this — widen the recall net and decompose the query rather than single-pass matching.

**3. Model-kit case — semantic scope miss.** "Do I have any model kits?" vs stored "plastic model airplane kit" is suppressed by the hardcoded candidate lifecycle gate: `defaultStrongLifecycleScore = 0.9` (`memoryrecall/search.go:22`, used in `DefaultLifecycleAllows` at `:120`), and the 8s embedding timeout silently falls back to BM25, which misses synonymy. **Quarq's dynamic standard/deep thresholding** and **HydraDB's `recency_bias`/adaptive `alpha`** both argue for replacing the fixed 0.9 with a query-class-adaptive threshold plus a parallel-BM25/merge fallback instead of silent degradation.

**4. Candidate lifecycle stall + no bidirectional feedback.** Autonomous drafts hardcode `ClaimStatusCandidate` at `Confidence: 0.7` (`autonomous_memory_drafts.go:159,162`) with no auto-promotion; promotion only fires on explicit `RetrievalFeedback.UsedRefs`, which answer-mode never emits — `accepted_ledger_evidence` stays metadata-only. So candidates sit dormant *and* are gated at 0.9. **Quarq's background consolidation with ingestion sync** (synchronous commit on eval boundaries) and its accepted-evidence loop map directly: answer-mode accepted rows should auto-emit feedback to advance lifecycle.

## 4. Recommendations, prioritized

**R1 — Replace ledger slot-matching with semantic term matching. (Touches `internal/rlm/env/tool_exec.go`; effort M; constraint: low.)** Swap the regex `matched_terms` vs `required_terms` substring logic in `classifyEvidenceLedgerRow` for embedding-cosine matching of required slot terms against evidence spans (reuse the existing embedder via `semantic.NewEmbedderFromConfig`). Borrow **Quarq's** ACCEPT/REJECT + entity-isolation rules as the decision policy; borrow **HydraDB's** entity-anchored matching as the conceptual frame. This directly fixes the coupon case and removes a banned keyword heuristic. *Quarq's prompt-only 500-line grounding rulebook does NOT transfer wholesale* — foxctl should keep deterministic, testable functional-core classification, just semantic instead of substring.

**R2 — Add a REQUIRED_DATA-style targeted fallback re-query. (Touches `internal/rlm/llm_runner.go`, `internal/rlm/env/tools.go`; effort M; constraint: low.)** When the evidence ledger has no ACCEPT rows (or the model flags insufficiency), extract the answer's target nouns and run one bounded re-query at a lower threshold before synthesis, merging deduped by ref ID. This is **Quarq's single largest contribution** and foxctl's single largest gap. Implement the insufficiency signal as a typed field on the RLM result (not a magic string), and cap to one fallback to avoid loops. Fixes degree + model-kit retrieval misses. *Quarq's LangGraph orchestration does NOT transfer* — keep foxctl's sequential Go runner; this is just an extra bounded stage.

**R3 — Adaptive candidate gate + parallel-BM25 fallback. (Touches `internal/intelligence/retrieval/memoryrecall/search.go`; effort S; constraint: low.)** Replace the hardcoded `0.9` candidate threshold and 8s silent-fallback with a query-class-adaptive threshold (Quarq's 0.38 standard / 0.28 deep) and run BM25 in parallel with vector, merging when vector is ready instead of falling back silently. Add `recency_bias`-style weighting (**HydraDB**) keyed off foxctl's existing temporal envelope. Fixes model-kit suppression.

**R4 — Wire named-memory recall as a first-class mixed lane. (Touches `internal/context/contextengine/retrieve_lanes.go`, `retrieve_mixed.go`; effort M; constraint: low.)** Promote `NamedMemoryRecallPack` from optional `ContextPackFunc` fallback to a native lane fused in `RetrieveMixed`, with HyDE-style relational decomposition for entity queries. Borrow **Quarq's** query decomposition rules; this leverages foxctl's existing lane-fusion seam rather than greenfield.

**R5 — Close the bidirectional feedback loop. (Touches `internal/rlm/llm_runner.go`, `internal/context/contextengine/retrieval_feedback_effects.go`, `autonomous_memory_drafts.go`; effort M; constraint: low.)** Auto-emit `RetrievalFeedback` with `UsedRefs` derived from `accepted_ledger_evidence` after answer-mode runs, so `ContextEventFromRetrievalFeedback` advances candidate→current. Add a deterministic confidence-and-usage promotion rule (pure functional core). Borrow **Quarq's ingestion-sync** idea for eval boundaries (synchronous commit before next case). Fixes lifecycle stall.

**R6 (later) — Context-enriched chunking + valid-time graph edges + decay scoring. (Touches `internal/intelligence/indexing/embedding/`, `contextengine/impact*.go`, `staleness.go`; effort L; constraint: low.)** Borrow **HydraDB's** design ideas only: enrich memory bodies with surrounding context before embedding (treat the enrichment LM like the existing context-updater), add valid-time metadata on impact edges (foxctl already supports supersession-not-overwrite), and implement a deterministic Ebbinghaus decay-with-reinforcement score for staleness as a pure function. No HydraDB dependency.

**Honest non-transfers:** Quarq's FAISS (`IndexFlatIP`) needs CGO/native libs — **does not transfer**; foxctl must stay on its SQLite/CAS embedding queue with pure-Go vector math or Turso. Quarq's ~$5/question gpt-4.1 spend and LangGraph DAG **do not transfer** — foxctl is model-agnostic and cost-sensitive. HydraDB as a backing store **does not transfer** at all (hosted REST, no Go SDK, no on-prem, violates WASI `network:"none"`).

## 5. What NOT to do

- **Do NOT adopt HydraDB as a backing store.** It is a network service with Bearer auth, no Go SDK, no self-host path — a direct violation of foxctl's no-egress/WASI posture and local-first SQLite/CAS/Turso storage. Borrow its *graph/temporal/decay design*, not the product.
- **Do NOT pull in FAISS or `sqlite-vec`.** Both require CGO/native extensions, which foxctl hard-rejects (CGO off, Turso-only SQLite-family path). Quarq's correctness comes from its retrieval *logic*, not specifically FAISS.
- **Do NOT port Quarq's disabled structured extractors wholesale.** They are deterministic markdown/table/list parsers Quarq itself bypasses; they re-introduce exactly the brittle keyword/pattern heuristics foxctl bans. If anything, use them only as a *supplementary high-confidence candidate source* gated behind explicit schemas, never for routing/classification decisions.
- **Do NOT re-implement the ledger as a 500-line prompt rulebook.** Quarq's grounding lives in giant model prompts; foxctl's principle is a deterministic, testable functional core. Make ledger classification semantic but deterministic — not prompt-driven.
- **Do NOT add unbounded fallback re-query loops.** Cap REQUIRED_DATA to one fallback (as Quarq does — "FORBIDDEN from using REQUIRED_DATA flag again") to avoid latency/cost blowups and non-determinism in golden tests.
- **Do NOT use magic-string flags** (`flags=["REQUIRED_DATA"]`) on the wire — model the insufficiency signal as a typed field, per foxctl's boundary-parsing principle.

2. **Adaptive candidate gate + parallel BM25 (R3).** In `internal/intelligence/retrieval/memoryrecall/search.go`, make `defaultStrongLifecycleScore` (`:22`) a query-class-adaptive parameter (standard 0.38 / deep 0.28) and run BM25 concurrently with vector, merging on vector-ready instead of silent timeout fallback. Add a test for the model-kit synonymy case. Independently shippable; fixes model-kit.

3. **Bidirectional feedback auto-emit (R5).** In `internal/rlm/llm_runner.go`, after answer-mode synthesis, derive `RetrievalFeedback.UsedRefs` from `accepted_ledger_evidence` and call `RecordRetrievalFeedbackWithEffects` so candidate claims promote via the existing event path. Add a test asserting a cited accepted row advances a candidate claim to current. Independently shippable; unblocks the lifecycle stall and makes R2/R4 measurably effective.

These three are ordered so each lands on an existing foxctl seam (ledger, recall, feedback effects) with its own unit test, no cross-dependency, and no constraint risk (no CGO, no network, deterministic functional-core changes). R2 (REQUIRED_DATA fallback) and R4 (named-memory lane) follow as the next slice once R1/R3 prove the retrieval-quality gains.
